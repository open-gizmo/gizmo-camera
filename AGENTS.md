# Agent instructions

For AI agents (Claude Code, Codex, Copilot and others) working on this repository. `CLAUDE.md` imports this file, so every agent reads the same rules.

## What this project is

Gizmo Camera turns an AI Thinker ESP32-CAM into a Wi-Fi snapshot camera.

- `microcontroller/` is the PlatformIO firmware for the ESP32-CAM (OV2640 sensor, flash LED, 4 MB PSRAM). It runs the camera, the Wi-Fi setup (from gizmo-common), and the HTTP server with the camera API, the MCP server for AI agents (`/mcp`) and their Markdown guide (`/llms.txt`).
- `webapp/` is the Nuxt 4 web app, embedded in the firmware: the Camera page, the device card and the Wi-Fi setup. It extends the [gizmo-common](https://github.com/open-gizmo/gizmo-common) web layer, and the mock device in `webapp/server/` answers like the firmware during development.

## Structure

- `src/main.cpp`: the entry point; starts logging, the camera, Wi-Fi and the web server.
- `src/camera`: starts the OV2640 and takes snapshots (`camera.*`), with the resolutions and the request options kept hardware-free in `capture_options.*`. The pins are in `camera_pins.h`.
- `src/mcp`: the MCP server (`mcp_protocol.*`), the base64 encoder that streams snapshots into its results (`base64_stream.*`), and the guide for agents (`agent_guide.*`), all hardware-free.
- `src/server`: the routes of the camera (`/api/camera`, `/api/capture`), the MCP server (`/mcp`), the guide for agents (`/llms.txt`, and `/` for clients that ask for Markdown) and the embedded web app (the Wi-Fi setup and device routes come from gizmo-common).
- `src/wifi`, `src/config`, `src/serial`: the Wi-Fi setup names, the project name and web server, and the serial log.
- `src/webui`: generated by `npm run build:embedded`, never edited by hand.

The firmware starts the camera while the PSRAM is free, then serves the web app and the camera API. A snapshot is taken in the web server task and streamed straight from the frame buffer, which goes back to the camera when the response ends.

## Working rules

1. Keep the split between firmware and web app clear: no device logic in the web app, no front-end behavior in the firmware.
2. Keep the module boundaries of `microcontroller/src/`: extend the right module instead of adding logic to `main.cpp`.
3. Keep hardware-free logic (`camera/capture_options.*` and everything in `mcp/`) free of hardware headers, and test it with `pio test -e native`.
4. The MCP server speaks the 2026-07-28 revision and the earlier ones that open with `initialize` (most clients still do): keep both working, and check the spec at modelcontextprotocol.io before changing the protocol.
5. ArduinoJson 7 keeps a pointer to a `const char *` instead of copying it: copy any text that isn't a literal (`JsonString(text, JsonString::Copied)`).
6. When a route, payload or validation rule changes, update the firmware handlers, the mock device in `webapp/server/` and the web app together, and translate every new error ID.
7. Never read GPIO0 as a button: on the ESP32-CAM it is the clock of the camera.
8. Prefer small, hardware-aware changes: no blocking calls, no needless allocations, no broad refactors unless they are needed.

## With every change

1. **Write the changelog.** When a maker would notice the change (a feature, the web app, the hardware or wiring, the setup steps, a fix), add a line under `## Unreleased` in [CHANGELOG.md](CHANGELOG.md), in the same commit. Write it for the people who flash and use the gadget, not as a commit message: what changed for them, and what they need to do (flash again, rewire, set something up again). Internal changes (refactoring, tests, CI) need no line unless they change what the gadget does.
2. **Keep the docs in sync.** Update the README (and its screenshots in `docs/` when the web app looks different), and tell the user when the gadget's page on [opengizmo.dev](https://opengizmo.dev) needs the same change.
3. **Check it before calling it done.** Run the tests (`pio test -e native` in `microcontroller/`, `npm test` in `webapp/`) and the release build (`npm run build:embedded` in `webapp/`, then `pio run -e release`).

## Releasing

Follow "Releasing a new version" in the README. The version's notes must be moved from `## Unreleased` to a `## vX.Y.Z - YYYY-MM-DD` heading in CHANGELOG.md: they become the GitHub release notes, and the release workflow stops before building anything when they are missing or when notes are left under Unreleased.

Every OpenGizmo gadget has its own release workflow file, and they are kept the same apart from the gadget's name and module (chip), which sit in the `env` block at the top. When you change one, make the same change in the others.

Work on the `feature` branch; changes reach `develop` and then `main` one step at a time, only for a release.
